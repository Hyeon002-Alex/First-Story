# 인계문서 — 4단계 H대주제: 전투 조립·구동

- **상태**: `완료` (통합 프로브 통과 → 코드 리뷰 → 리뷰 반영 → 본 문서. 4순차 정규 종료)
- **작성 기준**: 리뷰 반영 후 최종 코드
- **선행 대주제**: A(데이터·유닛), B(AP·명령서·intent·턴루프), C(한방 실행 파이프), D(대응·방어·특수판정), E(상태이상·턴종료), F(웨이브·전투불능·승패), G(적 AI 결정 로직) — 조립부가 이들이 만든 시스템을 배선한다.
- **핵심 한 줄**: A~G의 검증된 시스템 블록들을 `EncounterData`(정적 정의)로부터 **하나의 굴러가는 전투로 조립하는 시임**. F에서 이월된 `EncounterData` 부채 회수. 단, **"조립 완료 ≠ 플레이 가능"** — 아군 명령 입력은 별도 대주제로 분리 확정.

## ② 핵심 구조

`EncounterData`(정적 정의)를 조립부가 읽어 런타임 전투를 구성한다. 밸런스 값(스탯·배율)은 참조된 각 SO가 소유하고, 인카운터는 "무엇을 모으나"만 정의한다(SSOT 유지).

```
[Data]  EncounterData(SO)
          ├─ DefaultParty : AllyUnitData[]        (DG-1 안B)
          ├─ Waves        : Wave[] → EnemyUnitData[]
          └─ Patterns     : BehaviorPatternData[]  (DG-2 안A)
                    │
[Systems] BattleBootstrapper.Build(encounter)  (DG-3 안A: 순수 static)
                    │  1. 파티 생성
                    │  2. 패턴 → patternId 레지스트리(중복·null 검증)
                    │  3. 웨이브 전체 선인스턴스화(적별 patternId 등록 검증)
                    │  4. 공유 활성 적 리스트 seed
                    │  5. 6단계 배선
                    ▼
              BattleContext { Flow, Allies, ActiveEnemies, CurrentWaveIndex, HasNextWave }
```

**공유 활성 적 리스트(가장 중요).** `activeEnemies` **한 List 인스턴스**가 `WaveSystem`·`ActionResolver`·`BattleFlowSystem` 세 곳에 그대로 주입된다. 웨이브 전환은 `WaveSystem`이 이 리스트를 `Clear` + 다음 웨이브 재삽입하는 방식이라, 같은 인스턴스를 공유해야 전환이 세 시스템에 전파된다. `waves[0]`(아카이브)과는 별 인스턴스로 seed해 전환 시 아카이브 훼손을 막는다. `ProtectionSystem`도 동일하게 세 시스템이 한 인스턴스를 공유해야 선언된 보호가 실행에 보인다.

**배선 순서(의존: 무상태·독립 → 조합).** `IntentSystem`·`ProtectionSystem`(무인자) → `WaveSystem` → `ActionResolver`(executor) → `EnemyBehaviorSystem`(레지스트리+intent) → `BattleFlowSystem`(전부 조합).

## ③ 공개 인터페이스

**`EncounterData` (Data)**
```csharp
string                              EncounterId
IReadOnlyList<AllyUnitData>         DefaultParty
IReadOnlyList<EncounterData.Wave>   Waves      // 순서 = 웨이브 순서
IReadOnlyList<BehaviorPatternData>  Patterns

// 중첩 Wave (직렬화 래퍼)
IReadOnlyList<EnemyUnitData>        Wave.Enemies
```

**`BattleBootstrapper` (Systems)**
```csharp
static BattleContext Build(EncounterData encounter)   // 데이터 결함은 배선 전 InvalidOperationException으로 조기 차단
```

**`BattleContext` (Systems)** — 리뷰(M1) 반영으로 축소된 표면
```csharp
BattleFlowSystem            Flow             // 구동: Flow.ExecuteTurn() 반복
IReadOnlyList<AllyUnit>     Allies
IReadOnlyList<EnemyUnit>    ActiveEnemies     // 현재 웨이브. 전환 시 내용 교체되는 공유 리스트의 읽기 뷰
int                         CurrentWaveIndex  // WaveSystem 위임(라이브 값). WaveSystem 자체는 비노출
bool                        HasNextWave
```

**구동 계약**: `while (ctx.Flow.ExecuteTurn() == BattleOutcome.Ongoing) { }` → 종료 시 `Victory`/`Defeat`. 웨이브 전환은 `Ongoing`에 흡수(Step9 내부에서 `AdvanceToNextWave` 호출).

## ④ 의존성

- **레이어**: `EncounterData`는 Data(참조 타입이 `AllyUnitData`·`EnemyUnitData`·`BehaviorPatternData` + `UnityEngine`뿐). `BattleBootstrapper`·`BattleContext`는 Systems. **`Systems → Core → Data` 단방향 유지**, 역참조 없음.
- **조립부가 배선하는 기존 시스템**: `IntentSystem`(B), `ProtectionSystem`(D), `WaveSystem`(F), `ActionResolver`/`IActionExecutor`(C), `EnemyBehaviorSystem`(G), `BattleFlowSystem`(B 턴루프). E(상태이상)는 실행 파이프 내부에서 참여(조립부가 직접 배선하지는 않음).
- **밸런스 값 소유**: 조립부·인카운터는 값을 갖지 않음. 계산·`Scale`은 `CombatCalculator` 단일 소유 유지.

## ⑤ 검증 결과 + 리뷰 결과·반영

### 통합 프로브 — `PASS 26 / FAIL 0`
검증군 7개:
- **H1 정상 조립**: 예외 없이 조립 + 핸들 채워짐.
- **H2 공유 인스턴스 동일성**: `activeEnemies`가 Flow·Resolver·Wave에 동일 인스턴스(3) + `protection` 동일 인스턴스(2). *(조립부 최중요 책임 — 리플렉션으로 직접 검증)*
- **H3 웨이브 아카이브**: 전 웨이브 선인스턴스화 + 활성 리스트 ≠ 아카이브[0].
- **H4 패배 경로**: 아군 passive → 적이 처치 → `Defeat` 유한 종료.
- **H5 전환·승리**: 적 강제 전투불능 → 실 루프 Step9가 전환(공유 리스트 전파) → 마지막 웨이브 → `Victory`.
- **H6 음성 검증**: 미등록 patternId / 빈 파티 / 빈 웨이브 / 패턴 중복 / null 파티 / null 적 → 전부 예외.
- **H7 결정론**: 동일 인카운터 반복 → 동일 결과·턴수.

> 아군 입력이 별도 대주제라, 승리·전환은 아군 공격이 아니라 적을 쓰기 통로로 직접 전투불능시켜 실 루프가 배선을 밟는지로 검증했다.

## ⑥ 확정 설계 결정 (근거)

- **DG-1 (안B)** — `EncounterData`가 기본 파티를 보유. *근거*: 지금 파티 편성/성장 시스템이 없어(묶음4 영역) 인카운터가 파티를 안 주면 조립부가 파티를 얻을 데가 없음. 자기완결이 조립·검증을 단순화. 파티 필드는 묶음4 편성 도입 시 대체되는 **seam**.
- **DG-2 (안A)** — 패턴을 `EncounterData`가 직접 참조. *근거*: 조립부 로직은 소스와 무관(등장 patternId 집합만 알면 됨)이라 순수 데이터 배치 결정. 자기완결이 프로브 단순화. 전역 카탈로그는 잡몹 재사용 중복이 아파지면 승격.
- **DG-3 (안A)** — 조립부는 순수 static C# 클래스. *근거*: 로그 프로토타입 우선·프로브 헤드리스 호출·5단계 회귀 승격 재사용. MonoBehaviour 래퍼는 UI 단계로 미룸.
- **아군 입력 분리 (신규 확정)** — 아군 명령 입력(정보대응·방어대응·행동 선택)은 H 범위가 아니라 **별도 입력/UI 대주제**. H는 "A~G가 하나의 굴러가는 루프로 조립됨"까지만 증명. *근거*: `BattleFlowSystem` Step5/6은 stub, Step7의 아군 분기는 자동 차례종료 — 아군 입력은 입력/UI 레이어이며 의도적으로 뒤에 옴. 조립(H)과 별개 관심사.
