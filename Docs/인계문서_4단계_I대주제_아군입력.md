## 0. 대주제 목표(달성)

동기 턴 루프를 요청/응답 코루틴으로 재구성해, 스크립트 응답자가 방어/행동 결정을 루프에 주입하도록 완성했다. **입력 배관만** 구현 — 실제 Unity UI(버튼·패널)는 별도 후속 대주제로 분리(확정 유지). 헤드리스 검증은 H와 동일 방식(mono-mcs + UnityEngine 스텁 + 리플렉션 조립). 명령 어휘는 기존 `ActionCommand` 팩토리 재사용, 신설 없음.

**소주제 5개 전부 완료**: I-1 입력 계약 / I-2 ResponsePhaseSystem / I-3 루프 코루틴화 / I-4 대응단계 배선 / I-5 행동단계 아군 입력 + 구동 API.

## 2. 핵심 구조

- **입력 프로토콜(갈래1 · 1b 방식)**: `ExecuteTurn`은 순수 `IEnumerator`. 입력 지점에서 **우리 요청 객체(`InputRequest`)만** `yield return`, Unity `YieldInstruction` 금지. UI는 `StartCoroutine`, 헤드리스/테스트는 `MoveNext()` 수동 펌프 → 결정론·테스트성 유지.
- **응답 통로(D3-B 확정)**: 코루틴은 `MoveNext`에 값을 못 넘기므로, **드라이버가 소스를 소유**하고 `InputRequest.Response` 슬롯을 채워 결정을 흐름으로 되돌린다. **흐름(`BattleFlowSystem`)은 입력 소스를 모른다.** 요청만 밖으로 내밀 뿐이다.
- **스텝 재-yield(D1-A 확정)**: 입력 필요 스텝(Step6·Step7)을 `IEnumerator` 반환으로 바꾸고, `ExecuteTurn`이 `while(s.MoveNext()) yield return s.Current;`로 재-yield한다. `ExecuteTurn`은 얇은 9스텝 조율자로 유지되고, 각 스텝이 자기 요청 생성·yield를 캡슐화한다.
- **대응단계(Step6)**: 생존 아군마다 `InputPhase.Defense` 요청 → 응답이 방어대응 유효 종류(`ResponsePhaseSystem.IsResponseKind`)면 `TryApply`로 검증·적용. EndTurn·부적격 종류는 무시(대응 포기).
- **행동단계(Step7)**: 속도순 정렬 후 각 차례에서, 아군이면 `InputPhase.Action` 요청 왕복, 적이면 `BuildCommand`(intent)로 즉시 명령 생성. 대응단계에서 이미 acted된 아군은 `IsStillValid`가 스킵(D5).
- **구동 API(D4 확정)**: `BattleContext.RunBattle(IPlayerInputSource)`가 동기 펌프. 헤드리스/프로브는 이 한 줄로 전투 완주. UI는 이걸 쓰지 않고 `context.Flow.ExecuteTurn()`을 자체 코루틴으로 비동기 펌프. 동기/비동기 경로가 분리된다.

## 3. 공개 인터페이스

```csharp
// BattleFlowSystem — I-3~I-5 확정분
public IEnumerator ExecuteTurn();                 // 요청 필요 지점에서 InputRequest를 yield
public BattleOutcome LastOutcome { get; }         // 펌프 완료 후 판정. 기본값 Ongoing
public int TurnNum { get; }                        // Step1에서 증가(지연 실행 관찰점)
// 생성자 불변: 입력 소스 미주입(D3-B). Step5는 private void 유지(Reveal 이연)

// ResponsePhaseSystem — I-2 + M1
public static bool IsResponseKind(ActionKind kind);   // Defense·Protection만 true. 유효 종류 집합 SSOT
public static bool TryApply(ActionCommand command, ProtectionSystem protection);
    // 적용 true / AP부족·대상무효 false / 스코프 밖 종류·null·비아군 주체 throw

// BattleContext — I-5/D4
public BattleOutcome RunBattle(IPlayerInputSource inputSource);
    // 동기 펌프. null 소스 → ArgumentNullException. 1000턴 초과 → InvalidOperationException(종료판정 결함 방어)

// (I-1 계약은 스냅샷과 동일: InputRequest / IPlayerInputSource / ScriptedInputSource)
```

**확정 구동 계약**(커밋 코드에 반영됨 — `RunBattle` 내부):
```csharp
do {
    IEnumerator turn = Flow.ExecuteTurn();
    while (turn.MoveNext())
        if (turn.Current is InputRequest req)
            req.SetResponse(inputSource.Resolve(req));
} while (Flow.LastOutcome == BattleOutcome.Ongoing);
return Flow.LastOutcome;
```

## 6. 확정 설계 결정(근거)

이번 세션 확정(D1~D5). 스냅샷 계획과 어긋난 D2·D3은 근거와 함께 재확정.

1. **D1-A · 스텝 재-yield** — Step6·Step7을 `IEnumerator`화해 `ExecuteTurn`이 재-yield. 인라인(B안)은 요청 생성 로직을 조율자로 끌어올려 "얇은 9스텝 조율자" 구조를 깬다. 재-yield 3줄은 결정론에 무해.
2. **D2 · 선택지 필드 UI 대주제로 이연** — 스냅샷 6절 결정4는 I-4 부착 예정이었으나 변경. 헤드리스 `ScriptedInputSource`는 선택지(유효 대상·지불가능 스킬)를 읽지 않고, 소비처(UI)는 후속 대주제. I-4에 부착하면 소비처 없는 죽은 필드 → M1 투기적 노출 교훈 위반. I-4·I-5는 요청 프로토콜(`Phase`·`DecidingUnit`·응답슬롯)만으로 배선 검증.
3. **D3-B · 드라이버가 소스 소유** — 스냅샷 8절("flow에 주입")과 2·3절("드라이버가 슬롯 채움")이 충돌. A안(흐름이 소스 직접 호출)은 흐름 내부 동기 호출이라 코루틴이 무의미해지고 비동기 UI를 못 붙인다 — 1b 방식 채택 이유 자체를 무효화. 3절(B안) 확정. 결과: `BattleFlowSystem` 생성자·`BattleBootstrapper.Build` 소스 주입 없이 불변.
4. **D4 · `BattleContext.RunBattle`** — B안이면 펌프를 커밋 코드에 둬야 함. 동기 헬퍼로 노출: 헤드리스/테스트는 한 줄 구동(결정론), UI는 미사용(자체 코루틴 펌프). 동기/비동기 경로 분리.
5. **D5 · acted 스킵** — `TryApply`가 대응 성공 시 `SetActed(true)`. `IsStillValid`에 acted 게이트 추가해 대응한 아군을 Step7에서 스킵. 적은 Step7 진입 시 acted=false(Step1 리셋)라 무영향. 근거: 대응행동한 유닛은 속도순 행동 미실행(ResponsePhaseSystem 정책).

## 7. 기술 부채

**해소**
- **M1**: 유효 종류 집합 SSOT화(`IsResponseKind`).
- **L5**: `CombatCalculator` 죽은 using 제거.
- **L6**: `Step5_InfoResponse` 스텁 소유 표시.

**미해소 이월**
- `ResponsePhaseSystem` AP 비용 하드코딩(방향방어 1·보호 1). 밸런스 값 → 데이터 자산 이관 대상. `APSystem._apGainPerTurn`·`_maxAP`와 동일 성격.
- **Reveal 미구현** — 은닉·공개 정보모델 시스템 필요. `ActionKind.Reveal`(스킬 없음)과 GDD "정보형 고유행동"(스킬) 모델 통일 필요. Step5는 스텁 유지.
- **방어대응가능 스킬(도발)** — `SkillData`에 자격 플래그 없음. 추가 시 `IsResponseKind` + `TryApply` switch만 확장(M1 반영으로 확장 지점 국소화됨).
- **선택지 필드(D2 이연)** — `InputRequest`에 유효 대상·지불가능 스킬 필드. UI 대주제 소유.
- `Debug` 전역 로거 의존(H L3 이월). 신규 코드도 동일 — 새 부채 아님.
- **L1** ScriptedInputSource가 `request.Phase` 무시(순서 큐만). 단계별 강제는 UI 선택지 몫. 프로브 도구 본질적 한계.
- **L2** `BattleContext`가 조회 핸들 + 구동 드라이버로 성격 확장. 원 주석이 구동 포함이라 위반 아니나 기록.

**개선(부채 아님)**
- `BuildOrder`의 tuple 요소 이름 명시화(`(unit: unit, slotIndex: slotIndex)`). name inference(C# 7.1)는 Unity Roslyn에선 되나 mono-mcs 6.8 등 헤드리스/CI 컴파일러에서 실패 → 5단계 `Tests/` 승격 대비 명시화. 의미 불변.
