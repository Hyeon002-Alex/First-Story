## 2. 핵심 구조

**정보확인(Reveal) 지속 범위 — 웨이브 단위로 확정.**
매 글로벌 턴(`Step3_AssignEnemyIntent`)에서는 적 intent만 새로 결정·리셋되고, `IsRevealed` 플래그는 그대로 유지된다. 리셋은 웨이브 전환 시점(`Step9_Judge`가 `WaveSystem.AdvanceToNextWave()`를 호출한 직후)에만 일어난다.

기존에는 `Step3`가 `IntentSystem.ClearAll()`을 호출해 매 턴 intent와 revealed를 함께 지웠다 — 이는 "정보확인은 그 턴에만 유효, 다음 턴엔 재확인 필요"라는 턴 단위 리셋(A안)이었고, 이번 세션에서 명시적으로 폐기했다.

`IntentSystem`은 이제 세 개의 초기화 통로를 가진다:
- `ClearAll()` — intent+revealed+cancelled 전부. 레거시. 외부(프로브 등)의 전체 리셋용으로만 남김.
- `ClearTurn()` — intent+cancelled만. **턴 경계**(`Step3`)가 씀.
- `ClearRevealed()` — revealed만. **웨이브 경계**(`Step9`)가 씀.

## 3. 공개 인터페이스 (변경분만)

```csharp
// IntentSystem — 신규 2개, ClearAll은 시그니처 불변(호출부만 이동)
public void ClearTurn();       // 턴 경계. intent+cancelled만 비움. revealed 유지
public void ClearRevealed();   // 웨이브 경계. revealed만 비움
public void ClearAll();        // 기존 유지. 셋 다 비움(레거시 전체리셋)
```

`BattleFlowSystem`의 생성자·필드·다른 공개 인터페이스는 변경 없음(L에서 확정된 8-param 그대로).

## 6. 확정 설계 결정(근거)

- **정보확인 지속 정책 = 웨이브 단위 지속(선택지 중 C안).**
  - 상황: `K_후속_GPT_추가명세_v1.0` §2.2가 이 정책을 다룬다고 L 인계문서가 참조하지만, 그 문서의 실제 본문이 프로젝트 Knowledge에 없음(제목만 참조되고 내용 부재). GPT 쪽 원문 확보 실패.
  - 영현이 이 세션에서 직접 결정. **A안(턴 단위 리셋, 기존 코드 상태) / B안(인카운터 전체 지속) / C안(웨이브 단위 지속)** 세 선택지를 제시했고 C안으로 확정.
  - 근거 1: `WaveSystem.AdvanceToNextWave()`가 이미 `ShieldSystem.ClearAll` / `EvasionSystem.ClearAll` / `ProtectionSystem.ClearAll`을 웨이브 전환 시점에 호출하는 기존 패턴이 있음 — "웨이브 = 상태 리셋 경계"가 이미 코드의 SSOT. Reveal도 이 경계를 따르는 게 정합적.
  - 근거 2: GDD §11.1 플레이테스트 기준("정보확인 시 대응이 실질적으로 바뀜", "예상 결과와 실제 결과가 일치")이 매턴 리셋(A안)과 지속적으로 충돌할 소지가 있음. 정보확인이 매턴 소모품이 되면 정보전보다 AP 페널티 게임에 가까워짐.
  - **주의(중요)**: 이 결정은 GPT 쪽 §2.2 원문과 다를 수 있다. 원문이 이후 확보되면 **반드시 대조**하고, 다르면 재논의.
