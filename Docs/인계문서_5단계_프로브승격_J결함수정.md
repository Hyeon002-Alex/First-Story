## 1. J 결함 2건 (Code SSOT로 발견 → 수정·검증)

J 인계문서(`인계문서_4단계_J대주제_...`)는 "완료 · PASS 27/0"이라 주장했으나, **커밋 코드는 명세와 불일치**했다. 코드가 진실(Code SSOT).

### 결함 A — BuildOrder tuple 미명시
- `BattleFlowSystem.BuildOrder`가 `(unit, slotIndex)` 미명시 → mcs 6.8이 C# 7.1 name inference 미지원, CS1061로 **컴파일 불가**.
- J 인계문서 §5·§7은 "명시화 회수 완료, 별도 fix 커밋"이라 주장 → **허위**. 계획된 4커밋(J-1/2/3/fix)이 `66fe17e` 하나로 뭉쳐지며 fix 유실.
- **수정**: `.Select((unit, slotIndex) => (unit: unit, slotIndex: slotIndex))` 명시화.

### 결함 B — InfoResponseSystem.TryApply no-op
- 커밋된 `TryApply`가 `Debug.Log` 후 `return true`만. **`SetRevealed`·AP `Consume`·`SetActed` 전부 미구현.** 정보확인 게이트가 안 켜지고, AP 안 깎이고, acted 게이트 안 걸림(정보대응한 아군이 그 턴에 또 행동 = GDD §409 위반).
- J 인계문서 §3·§6은 "적용 true(SetRevealed·AP 소모·acted)"라 명세 → 커밋 코드와 **정면 모순**. J 목표("정보 대응 배관 완성")의 알맹이가 통째로 누락됐던 것.
- **수정**: `return true` 직전 3줄 추가.
  ```csharp
  intentSystem.SetRevealed(enemy);
  APSystem.Consume(ally, apCost);
  ally.SetActed(true);
  ```

### 정합성 판정
J는 **사실상 미완성 상태로 "완료" 처리되어 커밋**됐다. 로컬에서 통과시킨 코드가 커밋되지 않은 것으로 추정. 실제 J 완료는 이 세션. K는 `IsRevealed`를 소비처로 삼는데 그 값을 켜는 유일 경로가 죽어 있어, 이 수정 없이는 K 검증 자체가 불가능했다.

## 2. 프로브 승격 (C 경로)

### 배치
```
First-Story/
├─ Assets/Scripts/...           (Unity 컴파일 — 진짜 UnityEngine)
└─ Tests/                       (Assets 밖 — Unity 무시, 커밋 포함)
   ├─ Stubs/UnityEngineStub.cs  (ScriptableObject·Debug·[SerializeField]·[CreateAssetMenu] 4개만)
   ├─ Probes/IProbe.cs          (I 대주제, 38 PASS)
   ├─ Probes/JProbe.cs          (J 대주제, 31 PASS)
   ├─ run.sh                    (회귀 러너. exit 0=PASS / 1=실패)
   └─ .gitignore                (_bin/ 제외)
```

### 경로 선택 근거 (C vs A)
- **C 채택**: mono-mcs 6.8 헤드리스 유지. asmdef **불가** — Data 6개가 `ScriptableObject` 상속이라 stub 없이 컴파일 안 되고, asmdef 안에선 stub과 진짜 UnityEngine 타입 충돌. Unity Test Runner엔 안 뜨는 병렬 파이프라인.
- J 인계문서·공정표의 "리플렉션 헬퍼 걷어내고 Tests/ + asmdef 승격"은 **자기모순**(헤드리스 유지 ⊥ asmdef). 표현 정정함. 진짜 asmdef 승격은 Data POCO 분리(대규모 리팩터링) 후 별도 대주제.

### 실행
- `bash Tests/run.sh` (리포 루트 또는 어디서나). 각 프로브를 (Assets/Scripts 전체 + stub + 프로브 1개)로 개별 컴파일 → 실행.
- 컴파일러: `mcs -langversion:latest` (mono 6.8). ValueTuple.dll 참조 불요(mcs 내장, BuildOrder 명시화 후).
- 결과: **I 38 / J 31 PASS, exit 0.**

### 조립 방식 (재작성 시 참고)
- 유닛·SO·스킬: 정상 생성자 + 통로 메서드(`SetAP`·`SetIncapacitated` 등). private 필드는 리플렉션 `Set` 헬퍼(타입 계층 순회 + 박싱 struct 대응).
- `BattleFlowSystem`: `FormatterServices.GetUninitializedObject` + 필드 주입. Step5/6/7은 private `IEnumerator`라 리플렉션으로 꺼내 수동 펌프.
- I-4(Step6/7 부분조립): no-op `IActionExecutor` 주입(관심사 = 요청 발행 패턴, 실행 로직 아님).
- I-5(RunBattle 완주): 실제 `ActionResolver`·`WaveSystem`·`EnemyBehaviorSystem`(빈 registry → 적 무행동) 조립. 실제 데미지로 적 처치 → Victory.
- `Debug.Muted = true`로 전투 로그 억제. `Console.OutputEncoding = UTF8`로 한글 출력.

## 4. 다음 착수: K 대주제 (조회·선택지 read layer)

전투 코어의 read/query 층. write/execute는 A~J로 완성됨. 3소주제, 한 세션 완주 예상.

- **K-1 정보 조회 API**: `IntentSystem.IsRevealed` 소비. 기본 공개(대상·방향) vs 정보확인 후 공개(행동명·부가효과·회피불가·면역) 구분 반환. 소비처 = `Step4_Reveal`(현재 미소비). 캐릭터별 공개 범위 차이(연/니아)는 GPT 미제공 → 기본 분할만, seam `// [캐릭터 스킬 설계 후 수렴]`.
- **K-2 선택지 계산**: `InputRequest`에 유효 대상 + 지불 가능 스킬 부착(I-D2 회수). AP 게이팅·전투불능 제외·targetRule 유효성.
- **K-3 예상 피해 노출**: 기존 `ActionResolver.PreviewDamage`를 K-1/K-2 산출에 배선(예상=실제 재사용).

**K 착수 시 `bash Tests/run.sh`로 회귀 확인 필수** — K가 `IntentSystem`·`InputRequest`·`BattleFlowSystem`(Step4)을 건드리므로 I·J 프로브가 파손을 감지한다.
