## 2. 핵심 구조

**방어위상 예상피해 파이프라인**
```
IntentSystem.GetAttackers(ally, enemies)          [M-2, 역참조 + Q1/Q3 게이팅]
  -> DefensePreviewSystem.Preview(ally, dir, ...)  [M-3, HasDamage 게이팅 + 가상자세 조립 + 계산]
    -> ActionResolver.PreviewDamage(enemy, ally, skill, hypotheticalStance)  [M-1, 계산 단일 경로]
  -> ChoiceQuerySystem.DefenseChoices                [M-4, EnemyUnit키→BattleUnit키 변환 + 부착]
    -> ActionChoice.IncomingPreviewDamages
```

**M-1 자세 오버라이드의 핵심 불변식**: `ComputeDamage(actor, target, skill, stance)`에서 `directionMod`는 호출자가 넘긴 `stance`로 판정하지만, `breakMod`(붕괴/균열 받는피해증가)와 `receivedDamageMod`(상태이상 받는피해증가)는 **항상 `target`의 실제 현재 상태를 직독**한다. "가상"이라는 성격은 호출 맥락에만 있고, `DefenseStance` 자료구조 자체나 계산 함수는 실제/가상을 구분하지 않는다 — 이 덕에 붕괴 상태인 아군을 방어위상에서 미리보기해도 정확히 반영된다.

**Q1~Q4 게이팅이 걸리는 지점**:
- Q1(미확인 제외)·Q3(범위 소속) → `IntentSystem.GetAttackers` 내부
- Q2(적별 개별 결과) → `DefensePreviewSystem.Preview`의 반환 타입(`Dictionary<EnemyUnit, DamageResult>`)
- Q4(보호 리다이렉트 미반영) → 별도 코드 없이 자동 충족. `GetAttackers`는 `intent.Target`(원 대상)만 보고, 리다이렉트는 `TargetingSystem.Resolve`(실행 전용) 소관이라 애초에 이 조회가 볼 수 없음.

## 3. 공개 인터페이스 (신규·변경분만)

```csharp
// ActionResolver (static)
DamageResult PreviewDamage(BattleUnit actor, BattleUnit target, SkillData skill);                       // 기존, 무변경
DamageResult PreviewDamage(BattleUnit actor, BattleUnit target, SkillData skill, DefenseStance stance);  // 신규(M-1)

// IntentSystem
IReadOnlyList<EnemyUnit> GetAttackers(AllyUnit ally, IReadOnlyList<EnemyUnit> enemies);                  // 신규(M-2)

// DefensePreviewSystem (신규 static, Systems/Execution)
IReadOnlyDictionary<EnemyUnit, DamageResult> Preview(
    AllyUnit ally, AttackDirection direction, IntentSystem intentSystem, IReadOnlyList<EnemyUnit> enemies);

// ChoiceQuerySystem
AllyChoices GetChoices(
    AllyUnit ally, InputPhase phase, BattleSnapshot snapshot, IntentSystem intentSystem = null);          // 4번째 인자 추가(옵션, 기본 null)

// ActionChoice
IReadOnlyDictionary<BattleUnit, DamageResult> IncomingPreviewDamages { get; }                             // 신규 필드
static ActionChoice Defense(
    AttackDirection direction, int apCost,
    IReadOnlyDictionary<BattleUnit, DamageResult> incomingPreviewDamages = null);                          // 3번째 인자 추가(옵션)
```

`PreviewDamages`(기존 필드)는 의미 무변경 — 대상별 예상피해로만 쓰임. `Defense` Kind는 이제 항상 `PreviewDamages.Count == 0`이고 `IncomingPreviewDamages`만 채워짐.

## 4. 의존성

- `DefensePreviewSystem`(Systems/Execution) → `IntentSystem`(Systems/Flow), `ActionResolver`(Systems/Execution, 동일 폴더), Core(`AllyUnit`/`EnemyUnit`/`BattleUnit`), Data(`SkillData`/`AttackDirection`/`DefenseStance`). Systems 내부 폴더 간 참조는 자유(asmdef가 강제하는 건 `Systems→Core→Data`뿐)라 위반 없음.
- `ChoiceQuerySystem`(Systems/Input) → `DefensePreviewSystem`(Systems/Execution) 신규 의존.
- `Systems→Core→Data` 단방향 위반 없음. 역참조 없음.

## 6. 확정 설계 결정 (근거)

- **Q1 미확인 게이팅 = 제외.** `GetAttackers`가 `IsRevealed` 게이트. 근거: GDD "정보확인 시 대응이 실질적으로 바뀜" + K-1 reveal 게이트 기존 패턴과 정합.
- **Q2 프리뷰 형태 = 적별 개별 결과.** `Dictionary<EnemyUnit, DamageResult>` — 합산 아님. UI가 합산이든 리스트든 자유 구성 가능하도록.
- **Q3 범위(Area) 소속 판정.** `TargetRule.Area`면 대표자와 같은 진영 전원 포함(대표자가 `AllyUnit`이면 어느 아군이든), `Single/FixedTarget/Self`는 대표자가 정확히 그 아군일 때만. `TargetingSystem.LivingSameFaction`(실행 전용, 진영 전체 명단 산출)과 관심사가 달라 재사용하지 않고 별도로 둠 — 여긴 "특정 아군 1명의 포함 여부"만 묻는 훨씬 좁은 판정.
- **Q4 보호 리다이렉트 미반영.** 별도 코드 없이 `intent.Target`(원 대상)만 봐서 자동 충족.
- **자세 오버라이드는 4-인자 오버로드로 분리, 3-인자는 wrapper.** 기존 실행 파이프(`ResolvePerTarget`)·공개 API(`PreviewDamage` 3-인자) 무변경 보존이 목적. `breakMod`/`receivedDamageMod`는 가상자세와 무관하게 항상 대상 실제상태 직독(§2).
- **`PreviewDamages`/`IncomingPreviewDamages` 필드 분리.** 코드리뷰 결정(§5 높음 항목). 필드 하나가 Kind별로 의미가 뒤집히는 것보다, 각 Kind가 자기 필드만 채우는 기존 파일의 확립된 패턴(`Skill`이 스킬 계열만 non-null, `Direction`이 방향방어만 non-None)에 맞춤.
- **`intentSystem` 옵션 파라미터, 기본값 null 채택.** K/L 프로브가 `GetChoices`를 3-인자로 12곳에서 호출 중이던 걸 이미 닫힌 대주제라 재수정하지 않는다는 프로세스 원칙(최소침습)에 따라 보존. null이면 `DefenseChoices`가 프리뷰 없이 오퍼만 산출하는 안전한 축소 경로.

## 7. 기술 부채

**해소**
- JProbe 컴파일 결함(`ally`/`enemy`/`infoCmd` 미선언, M선행작업 커밋 누락분) — 세션 시작 감사에서 발견, 영현이 반영.
- `IntentSystem.GetAttackers` 중복 정의 — 구현 중 자체 발견·제거(파일 끝 사본 삭제).
- `ActionChoice.PreviewDamages` 이중 의미 — 코드리뷰로 발견·반영(§5).

**이월**
- **`intentSystem` 누락 시 무증상 실패.** UI 대주제가 Step6에 `ChoiceQuerySystem.GetChoices`를 배선할 때 `Defense` 위상 호출엔 **반드시 `intentSystem` 인자를 넘길 것**. 안 넘기면 예외·경고 없이 방어위상 예상피해 기능 전체가 조용히 사라짐.
- `IntentSystem.GetView` 도달불가 빈 블록 — 청소 필요, 우선순위 낮음.
- `DefenseChoices`의 `GetAttackers` 3중복 호출 — 최적화 여지 있으나 현재 규모에서 불필요.
- **기존 K/L 이월 부채 전부 유효**: 전열 수호 방어대응가능 플래그(`ResponsePhaseSystem.IsResponseKind`), 스킬측 `PreviewDamages` 조회-확정 시차, 대응 AP 값 하드코딩(방향방어 1·보호 1), Global `Debug` 로거 의존.
- **회귀 카운트 신뢰성.** JProbe/KProbe/LProbe의 PASS 수가 과거 여러 인계문서마다 서로 다르게 기록되어 왔음(예: JProbe 27/31/32/33 등 문서마다 상이). 이번 세션 실측(28/36/24)을 현재 SSOT로 삼음 — 앞으로는 실제 실행 결과만 기록하고, 실행 없이 숫자를 문서에 적지 않을 것.
