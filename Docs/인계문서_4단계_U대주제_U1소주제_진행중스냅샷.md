## 2. 핵심 구조

**대주제 전체 아키텍처**: Presenter/View 2층 분리. 판단 로직(무엇을 그릴지, 클릭이 어떤 명령이 되는지)은 전부 Presenter(순수 C#)에 모으고, View(`MonoBehaviour`)는 바인딩만 하는 얇은 통로로 남긴다. U-1은 이 중 Presenter/ViewModel 층만 담당.

**`AllyInputPresenter`** — 대상선택 상태머신. `AllyChoices` 1건을 받아 클릭을 `ActionCommand`로 조립한다.

```
AwaitingAction ──SelectAction(대상불요: Defense/EndTurn)──▶ Committed
       │
       └─SelectAction(대상필요)──▶ AwaitingTarget ──SelectTarget──▶ Committed
                                        │
                                        └──────Back──────▶ AwaitingAction
```

`PresenterState` 3값(`AwaitingAction`/`AwaitingTarget`/`Committed`)으로 상태와 "결과 확정 여부"를 하나로 묶었다 — `HasResult`는 `State == Committed`의 계산 프로퍼티.

**ViewModel 5종 + 헬퍼 2종**: `ActionOptionVM`(행동 버튼), `TargetOptionVM`(대상 후보), `IncomingPreviewEntryVM`(방향방어 버튼에 붙는 예상피해 행), `IntentDisplayVM`(적 의도 표시), `UnitLabel`(BattleUnit→표시명 SSOT), `IntentDisplayMapper`(IntentView→IntentDisplayVM, 상태 없는 순수 변환).

## 3. 공개 인터페이스

```csharp
public sealed class AllyInputPresenter
{
    public enum PresenterState { AwaitingAction, AwaitingTarget, Committed }

    public AllyUnit Ally { get; }
    public PresenterState State { get; }
    public IReadOnlyList<ActionOptionVM> ActionOptions { get; }
    public IReadOnlyList<TargetOptionVM> TargetOptions { get; }   // AwaitingTarget 외엔 빈 목록(널 아님)
    public bool HasResult { get; }                                // State == Committed
    public ActionCommand Result { get; }

    public AllyInputPresenter(AllyChoices choices);                // choices null이면 ArgumentNullException
    public void SelectAction(ActionOptionVM option);                // 상태 위반/외부 VM/재입력 시 예외
    public void SelectTarget(TargetOptionVM target);                // 상태 위반/외부 VM/재입력 시 예외
    public void Back();                                             // AwaitingTarget 외 상태면 예외
}

public static class IntentDisplayMapper
{
    public static IntentDisplayVM ToVM(IntentView view);   // view null이면 null 반환(GetView 계약과 대칭)
}

public static class UnitLabel
{
    public static string Of(BattleUnit unit);   // null→null, 표시명 빈 문자열→Id로 폴백
}
```

ViewModel 5종은 전부 `public sealed class` + 생성자 주입 get-only 프로퍼티. `ActionOptionVM.Source`(`ActionChoice` 역참조)만 Presenter 내부 조립용이고 View는 안 읽는다는 게 규약(강제 아님, 주석으로만 표시).

## 4. 의존성

**asmdef**: `Laplace.UI` → `["Laplace.Systems", "Laplace.Core", "Laplace.Data"]`. 3개 다 직접 명시(전이 참조로 안 됨 — `Laplace.Systems.asmdef`가 이미 Core·Data를 직접 참조하는 것과 같은 이유).

**Presenter의 실질 의존 표면 (결정 A, 3절 참조)**: `AllyChoices`/`ActionChoice`(Systems), `AllyUnit`/`EnemyUnit`/`BattleUnit`/`ActionCommand`(Core), `SkillData`/`StatusEffectData`/`ActionKind`/`AttackDirection`(Data)만 참조. **`BattleSnapshot`·`IntentSystem`·`ChoiceQuerySystem`은 참조하지 않는다** — `AllyChoices`/`IntentView` 하나만 손으로 만들면 전투 상태 전체 없이도 생성·조작·검증 가능하다는 게 이 결정의 존재 이유이자 헤드리스 프로브 성립 조건.

`ChoiceQuerySystem.GetChoices` 호출과 `IntentSystem.GetView` 호출은 U-2(드라이버)의 책임 — Presenter/Mapper는 그 결과만 받는다.

**리뷰**: 4절 규정의 정식 "대주제 리뷰"(대주제 완료 시 트리거)는 **미실시** — U 대주제 자체가 아직 안 끝났다. 다만 구현 도중 자기 위반 점검 성격으로 다음을 발견·반영:

- 최초 설계 Q&A의 "결정 C"(`SkillData`에 표시명 필드 없음)가 **오류로 확인됨** → 실제로는 `DisplayName` 프로퍼티 존재. 정정 후 `SkillId` 대신 `DisplayName` 우선 사용, 빈 문자열일 때만 `SkillId`로 폴백(현재 `Skill_.asset` 등 GameData가 표시명 빈 상태라는 실측 근거로 폴백 추가).
- 라벨 용어를 코드베이스 SSOT("방향방어", "차례종료" — 공백 없음)에 맞춰 통일.
- `Contains` 가드(현재 `ActionOptions`/`TargetOptions`에 없는 VM으로 `SelectAction`/`SelectTarget` 호출 시 `ArgumentException`) 추가 — View가 Presenter가 준 인스턴스를 그대로 되돌린다는 암묵 계약을 코드로 강제.

## 7. 기술 부채

**미해소, 이월**:
- 미지불 행동(AP 부족 등)의 회색 비활성 표시 없음 — read layer(`ChoiceQuerySystem`)가 애초에 후보에서 제외. 원한다면 read layer 변경이 필요(U-1 밖, What 결정 필요).
- `SkillData`/`AllyUnit`/`EnemyUnit`/`StatusEffectData`의 실제 표시명 데이터 미입력(현재 GameData 에셋 전부 빈 값 또는 낡은 스키마 — `Skill_.asset`은 `_effectIds`라는 현재 클래스에 없는 필드명까지 남아있는 것으로 봐서 리팩터링 이전의 낡은 자산). U-4(플레이 데이터 저작)에서 해소 예정.
- 헤드리스 검증 패러다임이 U-2부터 깨짐(`MonoBehaviour` 도입) — 이미 U 착수 시점에 알려진 구조적 사실, U-5에서 `run.sh` 글롭을 `UI/Driver/`, `UI/View/` 제외로 조정 예정. U-1(Presenter)만 예외적으로 여전히 헤드리스 검증 가능.
- `Laplace.UI.asmdef`의 실제 Unity 에디터 컴파일 타임 유효성 — mono-mcs로는 검증 불가, Unity 에디터에서 열어야 확인됨(9절 필수 확인 항목).

**해소됨**: 결정 C 오류(6절), 라벨 용어 불일치(5절).

## 8. 후속 대주제(소주제) 훅 위치

**U-2(Driver)가 소비할 지점**:
- `ChoiceQuerySystem.GetChoices(ally, phase, snapshot, intentSystem)` 결과를 `new AllyInputPresenter(choices)`에 그대로 주입.
- `presenter.HasResult`를 폴링(또는 View 이벤트로 트리거)해 `true`가 되면 `presenter.Result`를 `InputRequest.SetResponse(...)`로 흐름에 되돌림.
- `IntentSystem.GetView(enemy)` 결과를 `IntentDisplayMapper.ToVM(view)`에 그대로 넘겨 적 의도 패널 바인딩.

**폴더**: `Assets/Scripts/UI/Driver/`(U-2), `Assets/Scripts/UI/View/`(U-3) — 둘 다 이미 존재하는 `Laplace.UI.asmdef` 안에 그대로 들어가면 됨. 새 asmdef 불필요.

**U-5가 손댈 지점**: `Tests/run.sh`의 `find "$ROOT/Assets/Scripts" -name '*.cs'` 글롭에서 `UI/Driver/`, `UI/View/` 경로 제외(`UI/Presenter/`만 잔류).
